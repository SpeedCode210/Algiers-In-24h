The proposed system is architected as a modular, three-tier application designed to solve the \textbf{Orienteering Problem with Time Windows (OPTW)} within the urban context of Algiers. The design emphasizes the separation of concerns through a layered architecture, ensuring that the mathematical optimization logic remains decoupled from the service delivery and the user interface.

\subsection{Core Logic Layer: AlgiersLIB}
The foundation of the application is \texttt{AlgiersLIB}, a standalone Python library dedicated to modeling the problem domain and implementing optimization heuristics. To ensure extensibility, it utilizes the \textbf{Strategy Design Pattern}. An abstract base class, \texttt{Solver}, defines the interface for all optimization procedures, allowing the system to remain "open for extension but closed for modification."

\subsection{Service Layer: Flask REST API}
Built with the \textbf{Flask} framework, this layer manages data persistence, request validation, and the execution pipeline. Following the \textit{KISS} principle, the system utilizes \textbf{CSV flat-files} for data storage, which is optimal for the static nature of the landmark dataset ($\approx 50$ points). 

A critical performance optimization in this layer is the \textbf{Two-Phase Distance Calculation}. Because the meta-heuristics evaluate millions of potential routes, querying a real-world routing API during the search phase would be catastrophically slow and expensive. Instead, a \textbf{memoization-based caching system} computes a fast Haversine (straight-line) distance matrix for the solver loops. The Mapbox Directions API is strictly reserved for the final output phase to fetch accurate road geometries. Furthermore, a dedicated schema layer (\texttt{request\_schemas.py}) ensures "Garbage In, Garbage Out" protection by validating user inputs before they reach the solvers.

\subsection{Interface Layer: Frontend and UX}
The frontend is developed using \textbf{Vanilla HTML5, CSS3, and JavaScript} to ensure a lightweight client-side footprint without the overhead of heavy frameworks. The UI is spatially divided to maximize usability: a left-hand configuration panel, a central interactive map canvas, a right-hand itinerary overlay, and a bottom KPI (Key Performance Indicator) dashboard.

A key feature of the interface is the preference weighting logic. The user visually ranks five specific landmark categories (\textbf{Attraction, Historical, Shopping, Religious, and Tradition/Art}). To dynamically adjust the importance of each category, the system converts the user-assigned rank ($r$) into a score multiplier ($W_r$) using an amplification coefficient ($C = 1.2$) across the total number of categories ($n = 5$):
\begin{equation}
    W_r = \left(\frac{n - r}{n - 1} - 0.5\right) \times C + 1
\end{equation}
Using this formula, the ranks from 1 (best) to 5 (worst) map to a targeted multiplier spread of $\mathbf{\{1.6, 1.3, 1.0, 0.7, 0.4\}}$. These weights are passed directly to the \texttt{ScoringService} to adjust the objective function of the selected solver.

To gamify the user experience and abstract the mathematical complexity of the solvers for non-technical users, the system maps each of its optimization algorithms to a specific "Pokemon" persona reflecting its operational behavior. This roster spans simple greedy approaches (e.g., \textit{Piplup}, \textit{Bunnelby}), advanced meta-heuristics and evolutionary methods (e.g., \textit{Mewtwo} for Tabu Search, \textit{Eevee} for Genetic Algorithms), up to an exact IBM ILOG CPLEX solver (\textit{Magnemite}) serving as the optimal baseline.


\subsection{User Operational Flow}
The interaction between the user and the three modules follows a deterministic workflow:

\begin{enumerate}
    \item \textbf{Initialization:} In the left panel, the user defines the global constraints: the time window (start/end times), the starting hotel, and the specific day of the week (which enforces dynamic opening/closing hours for the OPTW constraints).
    \item \textbf{Personalization:} The user ranks the five landmark categories via a drag-and-drop interface. The Frontend calculates the required weight multipliers ($1.6$ to $0.4$) and selects a Solver.
    \item \textbf{Request Orchestration:} The parameters are sent via an asynchronous AJAX request to the \texttt{/api/solve} endpoint.
    \item \textbf{Backend Execution (Pipe-and-Filter Pattern):}
    \begin{itemize}
        \item The \texttt{ProblemLoader} initializes constraints and validates the dataset.
        \item The \texttt{ScoringService} applies the rank formula to compute a weighted score for every landmark.
        \item The \texttt{SolverService} executes the selected strategy using the cached Haversine matrix for speed, operating under a strict \textbf{30-second maximum search time limit}.
        \item The \texttt{RoutingService} fetches final road-network polylines from Mapbox for the optimized path.
    \end{itemize}
    \item \textbf{Visualization and Comparison:} After computation, the central Mapbox canvas renders the route. The bottom bar displays four primary KPIs: \textbf{Total Stops, Total Time, Distance (KM), and overall Interest Score}. The right-hand \textbf{Tour Guide} overlay provides a step-by-step itinerary, detailing each node's category, point value, and allocated visit duration. The solution is also added to a \textbf{Ranking Table}, allowing the user to seamlessly benchmark different algorithms.
\end{enumerate}
